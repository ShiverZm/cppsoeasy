# 性能问题分析基本步骤
## 一、性能剖析

性能剖析的目标是寻找性能瓶颈，查找引发性能问题的原因及热点代码。在性能剖析阶段，通常需要借助于现有的profiling工具，如perf，WPR/WPA等。

（1）确定可能存在性能问题的业务功能，比如存在大量文件扫描、大量账户弱密码检查或者大量事件处理的功能

（2）构造场景对功能进行压力测试，使性能问题暴露出来，然后运行profiling工具对实际业务的运行情况进行记录，一般可以记录3到5分钟左右的时间

（3）profiling结束后，查看生成的性能数据。数据中记录的是代码执行过程中各函数运行时间所占的比例。找到占比较高的函数调用，进行优化

对实际业务进行性能剖析时的注意点：

（1）由于实际业务功能比较多，所以最好每次只针对单个功能进行性能分析，这样可以避免其他功能运行时对分析结果造成干扰

（2）运行的实际业务需要包含符号信息，这样才能在分析结果中看到函数名信息。windows 可以使用单独的pdb符号文件，所以debug和release版都可以使用。linux agent需要使用debug版的agent，或者自己本地编译的带符号信息的release版

（2）debug版相比release版多了一些额外的开销，主要消耗在tt_memmanager_alloc_debug这个函数调用上，这是因为debug 记录了每次内存分配的信息

（3）性能测试时关闭debug日志。因为debug日志很多时，打印日志也比较消耗性能，会对分析结果造成干扰

## 二、代码优化

代码优化需要根据发现的性能瓶颈（函数调用），结合相应的代码逻辑，针对性地进行改进。比如减少不必要的函数调用，优化代码执行流程等。

（1）首先需要对功能代码比较熟悉，这样才能将性能分析数据中的函数调用与具体的执行流程对应起来

（2）找到时间占比较高的函数属于那一块代码逻辑，分析其占比较高的原因，结合代码逻辑尝试找到减少函数调用次数或者用性能开销更小的函数进行替换的方案

（3）对修改后的代码再次进行性能测试，观察上一次占比较高的函数本次是否下降或消失，并对本次的结果再次进行分析和优化



性能剖析和代码优化一般需要反复进行，即性能剖析发现问题后，经过一轮代码优化，再对优化后的代码进行性能剖析，再次优化，直到达到最佳性能
